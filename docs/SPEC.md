## 1. 결정 요약

### 1.1 이 기획이 답하는 질문

프로젝트의 원칙은 다음 한 문장이다. **"리뷰어가 '단순하게 바꿔 달라'고 요청할 만한 변경은 병합하지 않는다."**

이 판단은 본질적으로 주관적이며, 어떤 단일 수치도 대신하지 못한다. 그래서 판단을 두 층으로 나눈다.

- **기계적 차단(FAIL).** 거의 모든 리뷰어가 단순화를 요구할 사례, 그리고 측정·테스트·설정이 약화된 사례를 결정론적으로 막는다. FAIL은 "리뷰어가 거의 확실히 수정을 요구한다"는 뜻이다.
- **리뷰 라우팅(트리거).** 수치로는 판별할 수 없지만 의심스러운 *모양*을 감지하면 사람의 **단순화 리뷰**를 필수로 만든다. 복잡도가 줄지 않고 옮겨진 경우, 분기를 숨기는 구문, 레거시 핫스팟 수정, 측정하지 못한 코드가 그 예다. 트리거는 "리뷰어가 반드시 봐야 한다"는 뜻이다.

cccc는 첫 번째 층의 핵심 측정기이고 두 번째 층에 신호를 공급한다. cccc 혼자서 프로젝트 질문에 답하지 않는다.

### 1.2 핵심 결정

1. **게이트는 하나가 아니라 묶음이다.** 복잡도(G1), 구조 lint(G2), 의존성(G3), 테스트·무결성(G4), 변경 분기 커버리지(G5), 단순화 리뷰(G6), 변이 테스트(G7)로 책임을 나누고, 집계 체크 `quality-gate` 하나만 필수 체크로 둔다(4절).
2. **G1의 차단 지표는 Cognitive Complexity(CogC) 하나다.** Cyclomatic Complexity(CC)는 v1에서 관측만 한다. cccc의 CC는 `?.` 하나, `case` 라벨 하나, 추출 함수 하나마다 1씩 올라 리뷰어의 판단과 어긋나고 함수 분할을 오히려 벌한다. Codex의 CC 12 공동 차단은 채택하지 않는다(5.2절).
3. **CogC 출발 한도는 15다.** 신규 단위는 `≤ 15`, 기존 단위는 `≤ max(15, 기준 점수)`. 기준 점수는 저장하지 않고 매 실행 기준 트리(B)를 같은 바이너리로 다시 측정한다. baseline 파일이 없으므로 PR이 고칠 수도 없고, 개선이 병합되면 래칫이 자동으로 걸린다(5.3절).
4. **단위 대응은 "확실하지 않으면 신규"다.** 별도 AST indexer를 만들지 않는다. 대응이 모호한 단위는 신규로 보아 절대 한도를 적용하고, 넘으면 작성자가 고칠 수 있는 FAIL(`UNMATCHED_OVER_BUDGET`)을 낸다. Codex의 "모호하면 INCONCLUSIVE"는 작성자가 고칠 방법이 없는 상태를 만들어 결국 형식적 승인을 낳는다(5.4절).
5. **측정이 불완전하면 닫힌다(fail closed).** cccc는 구문 오류 파일을 0/0으로 채점하고 exit 0을 반환하며, 읽을 수 없는 파일은 stderr에만 남기고 결과에서 뺀다. manifest 대조, `parse_errors`, stderr, 빈 출력을 모두 INCONCLUSIVE로 처리한다(6절).
6. **트리는 checkout이 아니라 git blob에서 직접 만든다.** PR이 `.gitattributes`에 한 줄을 넣어 모든 `.ts`가 UTF-16으로 체크아웃되면 cccc가 전부 건너뛰는 것을 재현했다(10절).
7. **G1~G3은 PR 코드를 실행하지 않는 게이트 서비스에서 돈다.** 필수 체크를 쓰는 App 키가 Actions에 있으면 같은 저장소 브랜치의 PR workflow가 읽을 수 있기 때문이다(10.1절).
8. **함수 분할 문제의 실질적 대응은 "분기 보존 신호와 리뷰 라우팅"이다.** 사용자가 제안한 함수 길이, 매개변수, 모듈 의존성, 테스트 결과는 실측에서 분할형 점수 조작을 거의 잡지 못했다. 길이 제한은 오히려 분할을 *보상*한다(7절).
9. **CC가 테스트 필요 수를 알려주지 않는다는 지적은 맞다.** 하지만 NPath는 도입하지 않는다. 테스트 충분성은 복잡도 게이트가 아니라 별도 테스트 게이트(G4, G5, G7)가 맡는다(8절).
10. **임계값은 리뷰어와의 일치도로 보정한다.** 핵심 성공 지표는 게이트 FAIL·트리거와 사람 리뷰어의 단순화 요청 사이의 정밀도와 재현율이다. 평균 복잡도 감소는 KPI가 아니다(13절).

## 2. 목표, 비목표, 적용 범위

### 2.1 목표

- 변경된 코드에서 리뷰어가 단순화를 요구할 만한 제어 흐름 집중을 결정론적으로 찾아, 작성자(사람 또는 AI)에게 정확한 단위·수치·한도로 돌려준다.
- 기존 복잡도 부채가 늘어나는 것을 막되, 그 부채 때문에 무관한 변경이 실패하지 않게 한다.
- 점수만 낮추는 변환을 사람 리뷰로 보낸다.
- 측정이 불완전할 때 절대 PASS를 내지 않는다.

### 2.2 비목표 (v1)

- 종합 품질 점수, AI 작성 여부 탐지, 범용 call graph 분석, NPath 구현, 다언어 의미적 단위 대응, 임계값 자동 완화, 무제한 자동 리팩터링.
- 평균·합계 복잡도의 개선을 목표로 삼는 것.
- 악의적인 기여자가 테스트 결과를 위조하는 것을 막는 것(10.3절).

### 2.3 적용 대상

AI가 생성했다고 표시된 부분이 아니라 **검증 대상 변경 전체**에 적용한다. AI 출처 표시는 신뢰할 수 없고, 같은 코드에 다른 기준을 적용할 이유도 없다.

| 분류 | G1 처리 |
|---|---|
| 제품·서버·클라이언트·운영 스크립트 소스 (`.ts .tsx .mts .cts .js .jsx .mjs .cjs`) | 차단 정책 적용 |
| `.d.ts` | P에서 제외(선언 전용). 구현이 들어 있으면 cccc가 점수와 오류를 함께 내므로 P에 탐지 규칙을 둔다 |
| 테스트 코드 (P의 glob) | 측정하되 v1은 관측만 |
| 재생성 가능한 산출물, vendor | P의 manifest로만 제외. 제외 경로의 **신규** 파일은 S11로 라우팅 |
| `.vue .svelte .astro .mdx` 등 cccc가 다루지 않는 코드 형식 | `unmeasured`로 기록하고 S11로 라우팅. 조용히 통과시키지 않는다 |
| P에 등록되지 않은 코드 확장자 | INCONCLUSIVE |

"AI가 생성했다"는 이유로 generated 제외를 적용하지 않는다. 제외는 재생성 가능한 파생물에 대한 정책이다. 후보 브랜치의 `.gitignore`, `cccc.toml`, 파일 내부 주석은 범위 결정의 근거가 되지 않는다.

### 2.4 사람 PR과 AI 수정 루프의 차이

게이트 판정(G1~G7, 트리거)은 작성자와 무관하게 같다. 다른 것은 두 가지다.

1. 12.2절 금지 목록은 AI 수정 루프(P에 등록된 봇 계정)에만 기계적 FAIL로 적용된다. 사람이 같은 경로를 바꾸면 CODEOWNERS와 독립 승인으로 처리한다.
2. 자동 재시도와 조기 중단(12.3절)은 루프에만 적용된다.

AI 루프는 P에 등록된 봇 계정으로 식별하며, PR 본문의 자기 신고는 쓰지 않는다.

| C3 | 파일 합계에 module-level 코드 포함, module root CC 기본값 0 | **확인(보완)** | 최상위 `if`, `for…of`, `&&`만 있는 파일이 3/3. residue에는 최상위 문장뿐 아니라 **`static {}` 블록, 필드 초기화식, 객체 리터럴 값**도 들어간다. "+1 정규화"는 cccc 동작이 아니라 Codex의 설계 선택이다 |
| C4 | 파싱 오류가 있어도 복구된 일부 구문으로 결과가 생성될 수 있다 | **부분 확인. 실제 위험은 반대다** | JS/TS의 실제 구문 오류는 **파일 전체를 0/0으로 만든다**(오류 앞의 정상 함수까지 사라짐). 문맥 오류(최상위 `return`, async 밖 `await`, `??`와 `\|\|` 혼용)는 점수 전체와 오류를 함께 낸다. 어느 경우든 종료 코드는 0이다 |
| C5 | 분석할 파일이 없으면 exit 0 가능, 읽기 오류도 누락 가능 | **확인. 더 심각하다** | 일치하는 파일이 없으면 exit 0과 함께 **stdout이 비어 있다**(JSON 자체가 없음). 잘못된 UTF-8이나 권한 오류 파일은 `files[]`에서 빠지고 stderr에만 남는다. 명시한 파일이라도 확장자가 맞지 않으면 아무 메시지 없이 빠진다 |
| C6 | `cccc --no-config --no-cache --no-ignore --lang es -- a.ts b.ts` | **확인** | 유효하며 JSON이 기본 출력이다. 명시한 파일에는 `--no-ignore`가 의미 없다 |
| C7 | `--max-*`는 단일 실행 절대 한도 | **확인(보완)** | 엄격한 `>` 비교. module-level 코드는 보지 않는다. `--min`으로 숨긴 행도 실패로 집계된다. 캐시는 opt-in |
| C8 | 함수마다 CC 기본값 1 | **확인** | `engine.rs:174`. `if` 4개를 helper 2개로 나누자 ΣCC 5→7, CogC는 4 그대로 |
| C9 | TS/JS는 oxc 기반 | **확인** | v1.8.5는 oxc 0.155, v1.8.4는 0.154 |

### 3.2 Codex가 놓친, 설계에 중요한 사실

1. **구문 오류 파일은 0점이 되고 exit 0이다.** `--max-cognitive 0`을 줘도 통과한다. 1000단계를 넘는 중첩 리터럴도 `parse_errors`에 "file skipped"로 남고 파일 전체가 0점이 된다. 오류 파일을 거르지 않으면 "구문을 깨뜨리면 게이트 통과"가 된다.
2. **출력에 스키마 버전도 도구 버전도 없다.** 바이너리 해시와 `--version`을 따로 기록해야 한다.
3. **PR이 `cccc.toml`이나 `.cccc.toml`을 추가해 측정 범위를 바꿀 수 있다.** 설정 파일은 대상 경로가 아니라 **현재 디렉터리에서 위로** 탐색한다. PR이 넣은 `exclude=["src/**"]`가 `--max-cognitive 0` 실행을 출력 없이 exit 0으로 만드는 것을 확인했다. `--no-config`로 막힌다.
4. **캐시가 틀린 결과를 낼 수 있다.** 크기와 mtime이 같으면 파일을 읽지 않고 캐시를 믿는다. 내용만 바꾸고 mtime을 되돌려 오래된 결과를 재현했다. 캐시 파일에는 무결성 보호가 없다.
5. **파일 내부 억제 주석은 없다.**
6. **diff, baseline, changed-files, stdin 모드가 없다.** 공식 `moznion/cccc-action`도 기본값이 `version: latest`이고, 임계값을 저장소의 `cccc.toml`에서 읽으며, baseline 로직이 없다. 비교와 판정은 전부 직접 구현해야 한다.
7. **단위 식별 정보가 Codex 가정보다 약하다.** `<anonymous>`가 많고, 서로 다른 클래스의 같은 이름 메서드가 소속 없이 최상위 형제로 나오며, TS 오버로드 시그니처·`declare function`·abstract 메서드가 CC 1짜리 별도 행으로 나온다. 다만 같은 행의 여러 단위는 **소스 순서**로 나오므로 (행, 행 내 순번)은 쓸 수 있는 키다.
8. **성능은 문제가 아니다.** microsoft/TypeScript 26,851 파일을 4코어에서 0.48초, 25MB 파일 하나를 3.3초에 처리했다. `-j1`과 `-j4` 출력은 바이트 단위로 같다.

### 3.3 JS/TS 계산 규칙 (실측)

이 표가 계산 규칙 픽스처의 기대값이다. 도구를 바꾸거나 올릴 때 전체를 다시 검증한다.

| 구문 | ΔCC | ΔCogC | 비고 |

| `if` | +1 | +1 + nesting | |

| `??=` `\|\|=` `&&=` | **0** | **0** | 논리 연산으로 처리되지 않음. **점수 조작 경로**(7.2절) |

### 3.4 버전 안정성

- v1.8.4→v1.8.5에서 `cccc-core`는 바뀌지 않았다. `cccc-es`는 oxc 버전 상향과 API 변경 한 줄이며, 결과는 바이트 단위로 같았다.
- **지표 안정성 약속이 없다.** 마이너 버전에서 채점이 바뀐 이력이 있다(v1.4.0의 `?.`). oxc는 거의 매주 올라간다.
- 결론: 버전 범위가 아니라 **정확한 바이너리**를 고정하고, 업그레이드는 정책 변경으로 다룬다(6.1절).

### 4.2 병합 판정

```
병합 허용 ⇔ 모든 차단 하위 게이트 ∈ {PASS, NOT_APPLICABLE, ACCEPTED_WITH_WAIVER}
         ∧ (발화한 라우팅 트리거 없음 ∨ 유효한 단순화 리뷰 승인 있음 (7.6절))
         ∧ 기존 브랜치 보호(빌드, 타입체크, 1인 이상 승인)
```

집계 상태의 우선순위는 `FAIL` > `INCONCLUSIVE` > `ACCEPTED_WITH_WAIVER` > `PASS` > `NOT_APPLICABLE`이다. FAIL은 작성자가 지금 고칠 수 있고 INCONCLUSIVE는 대개 그렇지 않으므로 FAIL을 먼저 보여 준다. 관측 모드 게이트의 판정은 보고서와 보정 데이터로만 쓰고 집계에 넣지 않는다.

## 5. G1 복잡도 게이트 정책

### 5.1 측정 단위

**함수 단위.** `functions[]`와 그 `children`을 재귀적으로 모두 포함하며, 각 단위는 cccc가 준 **자기 점수**로 판정한다. 정책은 cccc의 두 가지 특성을 반영한다.

- **콜백은 nesting이 초기화되고 부모에 더해지지 않는다.** 그래서 로직을 인라인 콜백으로 옮기면 비용 없이 점수가 내려간다. 도구를 포크하지 않고 세 가지로 대응한다. G2의 `max-nested-callbacks` 차단, 트리거 S2, 그리고 모든 단위의 **포함 CogC**(자기 점수 + 모든 후손 점수) 기록이다. 포함 CogC는 v1에서 차단하지 않는다. 사소한 핸들러가 많은 컴포넌트를 부당하게 벌할 수 있어 shadow 데이터가 먼저 필요하다.
- **오버로드 시그니처, `declare function`, abstract 메서드는 CC 1, CogC 0인 별도 단위로 나온다.** CogC 한도에 걸릴 일이 없으므로 대응(5.4절) 오배정을 막는 데만 고려한다. S1·S10의 단위 수에서는 "CC 1, CogC 0, 자식 없음"인 단위를 뺀다.

**module residue 단위 `<module>`.** 파일마다 하나씩 만든다.

```
residue_cogc = file.cognitive − Σ(모든 깊이의 함수 cognitive)
residue_cc   = file.cyclomatic − Σ(모든 깊이의 함수 cyclomatic)
```

- residue에는 최상위 문장, `static {}`, 필드 초기화식, 객체 리터럴 값이 들어간다. `--max-*`로는 보이지 않는 영역이다.
- 함수 단위와 같은 CogC 규칙으로 판정한다. 이 단위가 없으면 로직을 필드 초기화식으로 옮겨 게이트를 피할 수 있다(실측: 함수 점수 0/1, residue 25/15).
- **불변식** `residue ≥ 0`. 위반은 도구 의미가 바뀌었다는 뜻이므로 `INCONCLUSIVE(INVARIANT_VIOLATION)`.
- Codex의 "+1 정규화"는 하지 않는다. CC는 관측만 하고 CogC에는 기본값이 없다.
- 알려진 한계: 필드가 많은 정상 파일(Angular 컴포넌트, 설정 객체)에서 오탐이 생기고, 클래스를 여러 파일로 흩으면 피할 수 있다. 전자는 shadow 보정으로, 후자는 트리거 S3로 다룬다.

### 5.2 지표와 임계값

| 지표 | v1 역할 | 출발 임계값 | 근거 |
|---|---|---|---|
| **CogC (단위 자기 점수)** | **차단** | **T = 15** | SonarSource의 JS/TS 기본값(S3776)과 같은 숫자여서 리뷰어가 이해하기 쉽다. 단 cccc에서는 Sonar보다 관대하다(3.3절). 12~15 구간은 S8로 기록해 강화 여부를 판단한다 |
| CogC (`<module>` residue) | **차단** | T = 15 | `static {}`·필드 초기화식 우회를 막는다 |
| CC (단위) | 관측 | 보고, 20 이상 표시 | `?.`·`case`·추출 함수마다 오르고 `??=`에는 오르지 않는다. 20-case dispatch `switch`나 `a?.b?.c?.d`는 높게 나오지만 리뷰어가 단순화를 요구하는 일은 드물다. 도구 간 차이(문제 ①)도 가장 크다. Codex의 CC 12는 optional chaining이 많은 평범한 코드를 실패시킨다 |
| 포함 CogC | 관측 + S2 (> 25) | — | Sonar의 람다 규칙을 근사한다 |
| 가시 분기 수, 단위 수, 단위당 CogC | 트리거 S1, S9, S10 | — | 재분배, 분기 은닉, 분할 밀도 신호 (7.5절) |

**CC 승격 규칙.** shadow 데이터에서 "CC ≥ X이면서 CogC ≤ 15인 단위"가 사람의 단순화 요청을 정밀도 0.6 이상으로 예측할 때만 CC를 보조 차단 지표로 승격한다. X는 분포에서 정하며 25~30 정도로 예상한다.

**상쇄 금지.** 지표는 각각 판정하며 가중 합산하지 않는다. 한 단위의 개선으로 다른 단위의 초과를 상쇄하지 않고("파일 전체로는 단순해졌다"는 근거가 되지 않는다), 한 지표의 개선으로 다른 지표의 악화를 상쇄하지 않는다.

### 5.3 신규·기존 판정식

C의 각 단위 u와, 대응하는 B 단위 m(u)(없을 수 있음, 5.4절)에 대해:

```
limit(u) = 15                        m(u)가 없음 (신규 또는 대응 불확실 → 신규 취급)
         = max(15, CogC_B(m(u)))     대응됨 (기존 부채 비악화)
FAIL(u) ⇔ CogC_C(u) > limit(u)
```

- 대응된 단위가 B에서 15 이하였다면 15까지 늘어날 수 있다. 모든 +1을 막으면 정상적인 기능 추가까지 무의미한 분할로 몰아가기 때문이다.
- 대응된 단위가 B에서 15를 넘었다면 **+1도 허용하지 않는다.** 줄이면 좋지만 의무는 아니다. 이런 단위를 수정하면 트리거 S5가 발화해 사람이 본다.
- **래칫은 저장하지 않는다.** B는 병합된 상태이고 매번 같은 바이너리로 다시 측정한다. 30을 22로 줄인 PR이 병합되면 다음 PR의 허용치는 자동으로 22다.
- **삭제된 단위**에는 규칙이 없다. 단 이름이 C 파일에 여전히 바인딩으로 남아 있으면 S11(단위 소실)이 발화한다.
- **부채 복제 금지.** C 단위 하나는 B 단위 최대 하나와, B 단위 하나는 C 단위 최대 하나와 대응한다. 기존 고복잡도 함수를 복사한 새 함수는 대응되지 않으므로 신규 한도 15를 받는다.
- 비교는 엄격한 `>`다. 15는 통과, 16은 실패. cccc `--max-*`와 같은 의미다.

**판정 예시** (가상의 수치)

| 유형 | B CogC | C CogC | 판정 | 이유 |
|---|---:|---:|---|---|
| 신규 | — | 15 | PASS | 한도와 같음 |
| 신규 | — | 16 | FAIL | `OVER_LIMIT_NEW` |
| 기존, 한도 이하 | 10 | 14 | PASS | 예산 안의 증가 |
| 기존, 한도 이하 | 10 | 17 | FAIL | `OVER_LIMIT` |
| 기존 부채 유지 | 22 | 22 | PASS + S5 | `legacy_debt` 표시, 리뷰 필수 |
| 기존 부채 악화 | 22 | 23 | FAIL | `LEGACY_WORSENED` |
| 기존 부채 개선 | 22 | 18 | PASS + S5 | 다음 PR의 허용치는 18 |
| 부채 복제 | 22 | 22, 22 | 하나 PASS, 하나 FAIL | 복사본은 신규 취급 |
| 대응 불확실한 고복잡도 | 22 | 21 | FAIL | `UNMATCHED_OVER_BUDGET`, B 후보 목록 제시 |

기존 부채를 유지한 PASS는 `legacy_debt: true`로 표시하며 "건강한 코드"로 표현하지 않는다.

### 5.4 변경 전후 단위 대응: "확실하지 않으면 신규"

**원칙.** 기존 부채 허용치(limit > 15)는 확실한 증거가 있을 때만 주는 특권이다. 대응이 없으면 신규이고, 오류는 항상 더 엄격한 쪽으로만 난다. 한도 이하 단위는 대응 여부와 무관하게 한도가 15이므로, 대응 문제는 **기존 고복잡도 단위**에만 영향을 준다.

**알고리즘.** `git diff -M --name-status B C`로 파일 쌍을 만든다(rename 유사도는 P의 값, 기본 70%). 내용이 같은 파일은 측정하지 않는다. 같은 바이너리에 같은 바이트는 같은 결과를 낸다. 파일 쌍마다 `git diff -U0 -M`으로 `lineMap: B행 → C행`을 만들고(hunk 내부 행은 대응 없음), 파일에서 최상위 단위, 다시 `children` 순으로 위에서 아래로 대응한다. 부모가 대응된 단위만 대응 후보가 된다.

1. **고정점 단계.** 선언 행이 수정되지 않은 경우(`lineMap(b.line)` 존재). 같은 `name`, 같은 `kind`, `line == lineMap(b.line)`, 같은 행 내 순번인 C 형제가 정확히 하나면 대응한다.
2. **같은 hunk 단계.** 선언 행이 수정된 경우(이름 변경, 시그니처 변경, `async` 추가). 같은 hunk 안에 같은 `kind`의 미대응 B 형제와 C 형제가 정확히 하나씩 있으면 대응한다.
3. **유일 이름 단계.** 이름 있는 단위만(`<anonymous>` 제외). 남은 형제 중 `(name, kind)`가 B와 C에 각각 정확히 하나면 대응한다. 파일 안의 순서 변경을 처리한다.
4. **그대로 이동 단계.** PR 안의 파일 간 이동(파일 분할). 미대응 B 단위와 미대응 C 단위가 같은 이름(익명 제외), 같은 kind, **같은 CogC와 CC**, 같은 자식 트리 모양(kind, CogC, CC)을 갖고 PR 전체에서 유일하면 대응한다. 점수가 같다는 것은 그대로 옮겼다는 증거이고, 허용치도 원래 점수를 넘지 않는다.
5. 나머지는 대응 없음. 미대응 C 단위는 신규, 미대응 B 단위는 삭제다.

2·3단계로 대응된 15 초과 단위는 `S5(identity-changed)`로 표시한다. 내용을 통째로 바꾸고 이름만 유지해 기존 허용치를 물려받는 경우를 사람이 확인하기 위해서다.

점수는 4단계의 동일성 확인 외에는 대응에 쓰지 않는다. "가장 가까운 점수" 같은 규칙은 가장 관대한 짝을 고르게 만든다. 이름은 NFKC 정규화와 혼동 문자(confusables) 검사를 거친다. 키릴 문자 `е`로 이름을 바꿔 다른 단위로 위장하는 경우를 막는다.

**단위 키.** waiver와 보고서에 쓰는 단위 키는 `(경로, children을 따라간 이름 사슬, kind, 같은 이름 형제 중 순번)`이며 C blob SHA에 묶는다. cccc는 소속 클래스를 주지 않으므로 클래스 이름을 키에 넣지 않고, 행 번호는 표시용으로만 쓴다.

**Codex의 AST indexer 방식과 비교**

| 항목 | Codex: 별도 AST indexer + fingerprint, 모호하면 INCONCLUSIVE | 본 설계: 행 대응 + 트리 + 신규 기본값 |
|---|---|---|
| 잘못된 통과(남의 허용치 승계) | indexer가 정확하면 낮다. 하지만 함수 경계가 cccc와 정확히 일치해야 하는 **두 번째 파서**다. 오버로드, 객체 accessor, 필드 화살표 함수에서 경계가 어긋나면 그대로 오배정된다. 문제 ①이 단위 경계에서 다시 생긴다 | 구조적으로 낮다. 허용치는 바뀌지 않은 선언 행, 같은 hunk의 1:1 수정, 유일 이름, 점수 동일 이동에서만 생기고, 그 경우에도 "이전보다 나빠지지 않음"으로 제한된다 |
| 운영 부담 | INCONCLUSIVE는 작성자가 고칠 수 없다. 게이트 담당자가 개입해야 하고, INCONCLUSIVE를 형식적으로 넘기는 습관이 생긴다 | 정체성이 모호해진 기존 고복잡도 단위라는 드문 경우에만 부담이 생긴다. 작성자가 (a) 15 이하로 줄이거나 (b) 모호해지는 편집을 피하거나 (c) waiver를 신청할 수 있는 FAIL이다 |
| 구현·유지 비용 | 두 번째 파서, fingerprint 정규화, 두 도구의 버전 고정, 경계 일치 픽스처 | `git diff -U0`과 cccc JSON 위의 약 200줄 |
| v2 판단 근거 | — | `UNMATCHED_OVER_BUDGET`을 shadow에서 기록한다. PR의 약 1% 또는 waiver의 약 10%를 넘으면 v2에서 indexer를 만든다. 그때는 어떤 사례를 풀어야 하는지 데이터가 있다 |

**결정: v1은 "확실하지 않으면 신규"다.** 잘못된 통과는 Codex 방식보다 많지 않고, INCONCLUSIVE의 한 범주를 통째로 없애며, 비용은 일부다. 장기적으로는 cccc에 열과 종료 위치 출력을 upstream에 제안하는 것이 가장 값싼 개선이다.

## 6. 측정의 재현성과 완전성 (문제 ①의 구현)

### 6.1 측정기 고정 (M)

- **바이너리.** cccc v1.8.5 릴리스 자산(Linux musl)을 쓴다. 도입 시 `gh attestation verify <file> --owner moznion --signer-workflow moznion/cccc/.github/workflows/release-build.yml`와 `gh release verify-asset`로 검증하고, sha256을 P에 기록한 뒤 조직 아티팩트 저장소에 미러링한다. 매 실행 전에 sha256을 P와 대조한다.
- **`moznion/cccc-action`은 쓰지 않는다.** 기본값이 `latest`이고, 임계값을 PR이 바꿀 수 있는 `cccc.toml`에서 읽으며, `actions/cache`로 결과를 캐시하고, baseline 로직이 없다.
- **M fingerprint** = {`cccc --version`, 바이너리 sha256, 인자 템플릿, Gate Runner commit, P revision}. 모든 `gate-result.json`에 기록한다. 같은 원칙을 ESLint, typescript-eslint, dependency-cruiser, Prettier(게이트 저장소 lockfile)와 커버리지 provider·버전(G5)에도 적용한다.
- **업그레이드는 P 변경이다.** (1) 3.3절 계산 규칙 픽스처 전체를 실행하고 모든 차이를 P 변경 설명에 적는다. (2) 최근 병합된 약 200개 PR을 새 바이너리로 B·C 모두 다시 측정해 판정 차이를 비교한다. (3) 그 후 병합한다. B와 C를 항상 같은 실행에서 같은 바이너리로 측정하므로 Codex가 말한 "재기준화"는 필요 없다. 다른 버전이나 다른 도구로 만든 두 보고서는 비교하지 않는다.
- **지표마다 측정기는 하나다.** ESLint `complexity`나 `sonarjs/cognitive-complexity`를 같은 지표의 판정에 함께 쓰면 같은 이름의 두 숫자가 `?.`, `switch`, 콜백에서 서로 다르게 나온다. 이것이 문제 ①에 대한 가장 직접적인 답이다.

### 6.2 B와 C의 구성

- **공식 판정은 merge queue의 `merge_group` 이벤트**에서 한다. C = `merge_group.head_sha`(실제로 병합될 commit), B = `merge_group.base_sha`. 병합 대상이나 후보가 바뀌면 이전 결과를 재사용하지 않는다.
- **사전 확인**은 `pull_request`에서 C = `refs/pull/N/merge`, B = 그 첫 번째 부모로 실행한다. 작성자와 AI 수정 루프를 위한 빠른 피드백이며 공식 판정을 대신하지 않는다.
- **트리는 git blob에서 직접 만든다.** `git ls-tree -r`과 `git cat-file blob`으로 manifest에 있는 파일만 임시 디렉터리에 쓴다. checkout과 `git archive`는 쓰지 않는다. 그래야 PR의 `.gitattributes`(`working-tree-encoding`, `filter`, `export-ignore`)가 측정 대상을 바꾸지 못한다. cccc는 파일 단위로 분석하므로 전체 트리가 필요 없고 비용도 작다. Linux에서 실행하며, 대소문자만 다른 경로 충돌은 INCONCLUSIVE다.
- **manifest**는 `git diff --name-status -M -C -z B C`에서 만든다.
  - 일반 파일(mode 100644, 100755)만 측정한다. 심볼릭 링크(120000)와 서브모듈(160000)은 `unmeasured`로 기록하고 S11로 라우팅한다.
  - P의 확장자 목록에 있고 P의 제외 목록에 없는 파일만 측정한다.
  - A는 C쪽, M·R은 양쪽, D는 B쪽만 측정한다(D의 B쪽 단위는 파일 간 이동 대응에 필요하다). C(복사)는 C쪽을 측정하고, T(타입 변경, 예: 파일이 `vendor/`를 가리키는 링크로 바뀜)는 `unmeasured`로 S11 라우팅한다.
  - LFS 포인터로 저장된 코드 파일은 INCONCLUSIVE.
  - 파일당 2MB를 넘으면 INCONCLUSIVE(크기 상한).
- **JSX가 든 `.js` 저장소**(CRA, Vite, Babel 관례)는 P 설정으로 해당 파일을 `foo.js.jsx`처럼 접미사를 붙여 측정한다. `foo.js`와 `foo.jsx`가 함께 있어도 충돌하지 않고, cccc는 이를 올바르게 라우팅하며 점수도 같다. 이 설정이 없는 저장소에서 JSX-in-`.js`는 작성자가 고칠 수 있는 INCONCLUSIVE다.

### 6.3 호출 계약

```bash
cd "$TREE_ROOT"                       # blob으로 만든 B 또는 C 디렉터리
env -i PATH=/usr/bin:/bin HOME="$(mktemp -d)" \
  "$CCCC" --no-config --no-cache --lang es -j 4 -- "${FILES[@]}" \
  >"$OUT/raw.$SIDE.json" 2>"$OUT/raw.$SIDE.stderr"
rc=$?
```

- 파일은 manifest와 같은 상대 경로를 인자 배열로 `--` 뒤에 넘긴다. 디렉터리, `--exclude`, `--min`, `--top-*`, `--max-*`, `--pretty`는 쓰지 않는다. 한도는 Gate Runner가 적용하므로 정상 종료 코드는 0뿐이다.
- 파일이 많으면 1,000개씩 나누어 실행하고, 각 결과를 따로 검증한 뒤 합친다.
- `--no-config`가 설정 탐색을 막지만, 이중 방어로 HOME과 환경 변수를 비운다.

**검증 항목 9개.** 하나라도 어기면 INCONCLUSIVE이며 사유 코드를 남긴다.

| 검사 | 사유 코드 | 막는 문제 |
|---|---|---|
| 바이너리 sha256 = P의 고정값, `--version` = `cccc 1.8.5` | `MEASURER_MISMATCH` | 측정기 바꿔치기 |
| `rc == 0` | `MEASURER_EXIT` | 한도를 넘기지 않으므로 1, 2는 모두 오류 |
| manifest가 비어 있지 않으면 stdout도 비어 있지 않음 | `EMPTY_OUTPUT` | 일치 파일 없음 → 빈 출력 + exit 0 |
| JSON 파싱 가능, 최상위 `files`·`summary` 존재, 각 단위에 5개 필드 존재 (`children`, `parse_errors` 부재는 빈 값으로 간주) | `SCHEMA` | 출력 형식 변경 |
| `files[].path` 집합 = manifest 집합, `summary.file_count` = manifest 크기 | `MANIFEST_MISMATCH` | 인코딩 오류·확장자 불일치로 조용히 빠진 파일 |
| stderr 비어 있음 | `MEASURER_STDERR` | `cannot read` 등 stderr로만 보고되는 오류 |
| C쪽 파일에 `parse_errors` 없음 | `PARSE_ERROR_CANDIDATE` | 구문 오류나 1000단계 초과 중첩으로 0/0이 되어 "전부 삭제됨, PASS"로 읽히는 문제 |
| 모든 파일의 residue ≥ 0 | `INVARIANT_VIOLATION` | 도구 의미 변경 |
| 실행 시간 < 120초 | `TIMEOUT` | |

- **B쪽 파싱 오류는 INCONCLUSIVE가 아니다.** 그 파일에는 기준이 없으므로 C의 모든 단위를 신규로 판정한다. 기준이 없으면 허용치만 사라질 뿐이다.
- **C쪽 파싱 오류의 안내.** 타입체크도 실패하면 "구문 오류를 고치라"고 안내한다. 1000단계 초과 중첩과 JSX-in-`.js`도 작성자가 고칠 문제다. `tsc`는 통과하는데 oxc만 거부하는 파서 지연은 P의 목록에 있는 문법일 때만 측정 override 대상이다(11.2절).
- **잘못된 UTF-8**은 작성자가 고칠 수 있는 INCONCLUSIVE다. 인코딩을 UTF-8로 바꾸라고 안내한다.

### 6.4 교차 검사

- **단위 소실.** B에서 단위가 4개 이상이던 C 파일의 단위가 0이고 행 수가 절반 넘게 줄지 않았으면 `INCONCLUSIVE(UNITS_VANISHED)`. 향후 oxc 복구 동작 변화를 방어한다. 단위가 적은 파일에서 이름 있는 B 단위가 사라졌는데 그 이름이 C 파일에 바인딩으로 남아 있으면 트리거 S11이다(`Function` 생성자 계열로 본문을 문자열로 옮긴 경우).
- **결정론.** 실행의 5%를 무작위로 골라 C를 `-j1`로 다시 실행해 바이트를 비교한다. 다르면 `INCONCLUSIVE(NONDETERMINISM)`이고 게이트 담당자에게 알린다.
- **반복 실행.** 같은 B/C/P/M이면 시간과 실행 ID를 뺀 정규화된 판정과 증거가 같아야 한다.

## 7. 함수 분할과 점수 조작 (문제 ②)

### 7.1 판단

함수 분할은 정상적인 개선 방법이면서 가장 쉬운 점수 조작 방법이다. **두 경우는 G1이 쓰는 수치로는 구별되지 않는다.** 실측에서 정직한 리팩터링(a)과 기계적 분할(b)은 파일 ΣCogC가 둘 다 15였고, 둘 다 호출처가 하나뿐인 helper를 만들었다(4개 대 11개). 그래서 최종 판정은 사람이 하고, 게이트는 의심스러운 모양을 찾아 리뷰로 보내는 일을 맡는다.

### 7.2 실측: 동작 보존 변환 17종

복잡한 가격 계산 함수(CogC 24, CC 17)에 변환을 적용하고 cccc v1.8.5로 측정했다. "가시 분기"는 V = Σ(단위 CC − 1) + residue CC, 즉 cccc가 볼 수 있는 결정 지점 수다.

| 변환 | 단위 수 | 최대 CogC / CC | ΣCogC | 가시 분기 V | Codex 설계 판정 | 분류 |
|---|---:|---|---:|---:|---|---|
| 원본 | 1 | 24 / 17 | 24 | 16 | FAIL | — |
| (a) 가드절, 의미 있는 helper, 표 하나 | 5 | 5 / 5 | 15 | 14 | PASS | **정당** |
| (a′) 같은 helper를 중첩 클로저로 | 4 | 9 / 8 | 16 | 16 | PASS | 정당 |
| (b) 공유 `ctx` 객체를 수정하는 helper 11개 | 12 | 2 / 4 | 15 | 16 | PASS | **조작** |
| (c) 화살표 함수 객체 맵 + `BOOL[String(cond)]` 디스패치 | 23 | 4 / 5 | 6 | 6 | PASS | 혼합 |
| (d) `[cond].filter(Boolean).forEach(…)`, 콜백 이동 | 8 | 2 / 4 | 9 | 10 | PASS | **조작** |
| (d′) `cond && (() => {…})()` | 5 | 4 / 6 | 13 | 15 | PASS | **조작** |
| (e) 로직을 클래스 필드 초기화식으로 | 4 | 0 / 1 | 0 (+residue 25) | 15 | 함수 PASS, **module FAIL (25)** | 조작 |

| (j) 전략 클래스, `reduce` 파이프라인 | 7 | 7 / 8 | 13 | 13 | PASS | 정당 (규모 대비 다소 과추상화) |

동작 동일성은 e′, e″를 뺀 15종에서 무작위 주문 5,000건으로 확인했다. 2차 레드팀에서 `Object.constructor.constructor("order", "user", body)`로 같은 결과(0 단위, 0/0, 동작 동일)를 내면서 `no-new-func`·`no-eval`·`no-implied-eval`에 모두 걸리지 않는 변형도 확인했다(10.2절 V17).

**결론.**

- Codex 설계가 잡은 것은 필드 초기화식·`static {}` 이동(module residue)뿐이며, 그것도 한 파일에 몰려 있을 때만이다.
- 가장 위험한 것은 **비용이 0인 구문**이다. 논리 할당(`&&=`, `||=`, `??=`)과 범용 조합자는 CogC 24 함수를 1~2로 만들고, Function 생성자 계열은 단위를 아예 없앤다.
- 분할하면 nesting 비용이 사라지므로 **ΣCogC는 보존되지 않는다**((b) 24→15). 보존되는 것은 가시 분기 V다((b) 16→16). 재분배 신호는 V로 정의해야 한다(7.5절 S1).
- 예외를 goto처럼 쓰는 변환은 `catch` 비용 때문에 효과가 없었다.

### 7.3 사용자가 제안한 보조 지표는 이 조작을 잡는가

ESLint 10.1로 같은 변형들을 두 번 검사했다. 1차는 엄격한 실험값(길이 40행, 문장 15개, 매개변수 3개, 콜백 중첩 2단계), 2차는 본 기획의 채택값(길이 60행, 매개변수 4개, 콜백 중첩 3단계)이다.

| 지표 | 1차 (실험값) | 2차 (채택값) | 판단 |
|---|---|---|---|
| **함수 길이** (`max-lines-per-function`, `max-statements`) | 분할형 조작((b)(c)(d)(f″))은 하나도 못 잡았다. 걸린 것은 원본, (f)(문장 수), (g)뿐 | **아무것도** 잡지 못했다(원본 포함) | 분할 대응책으로는 역효과다. 길이 제한은 분할을 **보상**한다. "평평하고 길게 여러 일을 하는 함수"는 CogC가 놓치므로 **트리거 S4**로만 쓴다 |
| **매개변수 수** (`max-params`) | 별칭 재귀(h, 매개변수 4개) 하나 | **아무것도** 잡지 못했다 | context 객체 분할은 매개변수를 1개로 만들어 **분할을 숨긴다**. 오탐이 적고 고치는 방법이 리뷰어 요구와 같으므로 신규 위반에 한해 차단(4개)은 유지하되, 분할 대응책으로 기대하지 않는다 |
| **콜백 중첩** (`max-nested-callbacks`) | 조합자(f″) | **아무것도** 잡지 못했다 (f″는 정확히 3단계) | 2단계는 `arr.map(x => p.then(y => …))` 같은 평범한 코드를 막으므로 3을 유지하고, f″는 S9·S10이 맡는다 |
| **모듈 의존성** | 단일 파일 표본이라 해당 없음 | 해당 없음 | 파일 간 분할과 residue 분산(e′)을 약하게 잡는다. **새 순환 의존은 G3에서 차단**, fan-out 변화는 트리거 S3 |
| **테스트 결과·커버리지** | **아무것도** 못 잡았다 | — | 모든 변형이 동작을 보존하므로 테스트는 통과하고, (f)(f′)(i)는 분기가 사라져 커버리지가 오히려 *쉬워진다*. 분할 조작 대응책이 아니다. 다만 "분할하면서 동작이 바뀐 경우"를 막는 필수 장치이므로 G4에서 차단 |
| 실제로 잡은 것 | `no-new-func`(i), `no-param-reassign {props}`(b), `no-restricted-syntax` 선택자(분기 은닉 구문) | `no-new-func`(i), `no-param-reassign {props}`(b, 11건) | 7.4·7.5절에 반영. 두 번째 측정기(ESLint `complexity`)도 (f)를 잡았지만 6.1절 원칙에 따라 채택하지 않고, (f)는 S9로 잡는다 |

Codex의 "이미 팀 규칙으로 운영 중일 때만 lint에 둔다"는 입장은 일부만 받아들인다. 복잡도 게이트에 넣지 않는 것, 저장소 전체에 보정되지 않은 규칙을 강제하지 않는 것은 맞다. 하지만 "이미 채택한 경우만"이면 게이트의 강도가 각 저장소의 우연한 lint 상태에 좌우된다. 그래서 P가 **최소 하한**을 정의하고 **신규 위반에만** 적용한다. 신규 위반으로 한정하면 Codex가 걱정한 기존 위반 정리 비용이 없다. 저장소는 더 엄격하게 설정할 수 있지만 더 느슨하게 할 수는 없다.

### 7.4 G2 구조 lint

**실행 방식.** ESLint는 PR의 `eslint.config.js`가 아니라 P의 설정으로, 게이트 저장소의 플러그인으로, **`--no-inline-config`**로 실행한다. `eslint.config.js`는 실행되는 JS이고, B에 이미 있던 `/* eslint-disable */`이 파일 전체의 P 규칙(`no-new-func` 포함)을 끌 수 있기 때문이다. 출력은 `-f json`이다(ESLint 10에서 `unix`, `compact` formatter가 빠졌다).

**신규 위반 판정.** 위반의 시작 행이 추가 행인지로 판정하지 않는다. `max-params`는 다섯 번째 매개변수를 6행에 추가해도 함수 시작 행에서 보고되기 때문이다. 대신 B와 C를 모두 검사하고 `(규칙, 대응 단위)` 기준으로 **C에 있고 B에 없는 위반**을 신규로 본다. 단위 대응은 5.4절 결과를 재사용한다.

| 규칙 | v1 | 이유 |
|---|---|---|
| `no-eval`, `no-new-func`, `no-implied-eval` + `no-restricted-syntax`로 `.constructor`를 통한 호출, 값으로 쓰인 `Function`, AsyncFunction·GeneratorFunction 생성자, `Reflect.construct`, 비리터럴 `import()`, `vm` 모듈 사용 | **차단** | 단위 소실((i), V17) |
| `@typescript-eslint/max-params` 4 | **차단** | 공유 지역 상태를 끌고 다니는 helper. `this`는 타입이 `void`일 때만 세지 않는다 |
| `max-nested-callbacks` 3 (테스트 파일 제외) | **차단** | cccc가 콜백 복잡도를 부모에 더하지 않는 맹점을 줄인다 |
| bidi 제어 문자(U+202A–202E, U+2066–2069) 금지 | **차단** | 사람 리뷰를 속이는 Trojan Source |
| 추가된 `eslint-disable*`, `@ts-ignore`, `@ts-nocheck`, 커버리지 ignore 주석 | **차단** (P 허용 목록 제외) | 다른 게이트 무력화 |
| `max-lines-per-function` 60 | 트리거 S4 | 7.3절 |
| `no-param-reassign {props: true}` (새 함수) | 트리거 S10 | 공유 context 수정형 분할 |
| `no-restricted-syntax`: 부수효과가 있는 논리 할당, IIFE, `[…][+x]`·`[…][Number(x)]`, 비교식에 단항 `+`, 값이 화살표 함수인 객체 리터럴, 원소 0~1개 배열 리터럴에 바로 붙은 `.forEach`·`.map`·`.filter` 등 | 트리거 S9 | 분기 은닉 구문. `cache ||= compute()` 같은 정당한 메모 패턴, 핸들러 맵 같은 정당한 클로저 표가 있어 차단하지 않는다 |
| `max-depth`, `max-statements`, `max-lines` | 관측 | CogC의 nesting 가산과 중복. 관측 데이터로 승격 여부를 정한다 |

### 7.5 리뷰 트리거

트리거는 FAIL을 만들지 않고 G6 단순화 리뷰를 필수로 만든다. 모든 트리거는 증거를 남긴다. 작성자와 AI에게 트리거의 존재와 의미를 공개한다. 숨겨서 얻을 것이 없고, "재분배는 사람이 본다"는 사실이 재분배 동기를 줄인다.

아래 조건은 2차 레드팀에서 7.2절 픽스처에 그대로 적용해 검증했다. 행 수 기반 조건은 형식 맞춤에 따라 크게 달라지므로(Prettier 적용 후 (b)의 단위 밀도가 10행당 6.7→1.9), **B·C 모두 고정된 Prettier로 정규화한 뒤** 행을 센다.

| ID | 조건 | 근거와 실측 |
|---|---|---|
| **S1 재분배** | 변경 파일(또는 PR의 파일 집합)에서 V(C) ≥ V(B) − 2 **이고** 단위 수 +3 이상 **이고** 최대 단위 CogC −5 이상(또는 대응 단위가 15 초과에서 15 이하로). V는 가시 분기(7.2절), residue 포함 | 분기는 그대로인데 단위로 나뉘었다. ΣCogC는 분할 시 nesting 비용이 사라져 보존되지 않으므로 쓰지 않는다((b) 24→15). ΣCC도 추출 함수마다 +1이라 쓰지 않는다. **정직한 리팩터링 (a)에도 발화한다**(V 16→14). 정밀도는 shadow에서 측정한다 |
| **S2 콜백 맹점** | 신규·변경된 익명 자식 단위의 CogC ≥ 8, 또는 자기 CogC ≤ 15인데 포함 CogC > 25 | cccc는 콜백 복잡도를 부모에 더하지 않는다 |
| **S3 모듈 분할** | 한 모듈에서만 import되는 새 모듈이 2개 이상, 또는 변경 파일의 efferent import가 5 이상 증가 | 파일 단위 분할로 단위·파일 한도 회피 |
| **S4 긴 함수** | 신규·재선언 함수가 공백·주석 제외 60행 초과 | 평평하고 여러 일을 하는 함수 |
| **S5 부채 수정** | B CogC > 15인 대응 단위의 **범위 안에** 변경이 있음. 범위는 시작 행부터 같은 깊이 이하인 다음 단위의 시작 행 직전까지(cccc가 종료 행을 주지 않으므로). 5.4절의 `identity-changed` 포함 | 핫스팟 수정. 점수 변화로 판단하면 레드팀의 V10 재현(24→24)을 놓친다 |
| **S6 waiver·override 요청** | 11절 | 위험 수용은 사람이 책임진다 |
| **S7 테스트 약화 의심** | assertion 수 감소, matcher 약화, 스냅샷 갱신 | 8.3절 |
| **S8 한도 근접** | 신규 단위 CogC 12~15 | **관측만, 라우팅하지 않는다.** 한도를 12로 낮출지 판단하는 자료 |
| **S9 분기 은닉** | 파일의 V가 30% 넘게 줄었는데 정규화 행 수 감소는 30% 미만, **또는** 분기 밀도(V/행)가 30% 이상 줄고 V가 3 이상 줄었음, **또는** G2의 분기 은닉 선택자 발화 | 행 수 조건만으로는 (f′)(f″)(i)를 놓친다. 조작 코드도 짧아지기 때문이다(38행→15~20행). 정당한 표 리팩터링에도 발화하므로 라우팅만 한다 |
| **S10 분할 밀도** | 변경 파일에서 단위 수 / (ΣCogC + 1) ≥ 0.6 **이고** 새 단위 5개 이상, **또는** 새 helper의 `no-param-reassign {props}` 위반 | 실측 발화: (b) 0.75, (c) 3.3, (d) 0.8, (i′) 0.85, (f″) 7.3. 미발화: (a) 0.31, (a′) 0.24, (j) 0.5, (d′) 0.36. 행 수에 의존하지 않아 형식 맞춤으로 피할 수 없다 |
| **S11 미측정·소실** | `unmeasured` 파일(SFC, 심볼릭 링크, 서브모듈, 타입 변경), 제외 경로의 신규 파일, `.gitattributes`·`.gitmodules` 변경, 이름 있는 B 단위가 사라졌는데 그 이름이 C 파일에 바인딩으로 남음 | 측정하지 못한 코드가 조용히 통과하지 않도록 사람이 본다 |

**여러 PR에 나눈 조작.** 모든 트리거는 한 PR의 B와 C를 비교하므로, 같은 변환을 여러 PR에 조금씩 나누면 피할 수 있다. 그래서 S1·S9·S10은 파일별 **이동 기준**(30일 전 또는 직전 5회 병합 시점의 상태)과도 비교해 계산한다. P1에서는 관측만 하고, 정밀도를 확인한 뒤 P2에서 라우팅에 포함한다.

**사용자의 시나리오에 적용하면.** CogC 28인 100행 함수를 CogC 4 이하 helper 10개와 호출부로 나누면 G1은 단위별로 통과하고, 분기 수가 그대로이므로 S1이 발화한다(V 유지, 단위 수 +10). helper가 공유 상태를 매개변수 5개 이상으로 넘기면 G2 `max-params`가 FAIL을 내고, context 객체로 넘기면 S10이 발화한다. G4는 테스트가 사라지지 않았음을 확인하고, G5(관측)는 helper의 분기가 실행되는지 보여 준다. G6에서 리뷰어는 "각 helper가 이름 붙일 수 있는 개념인가, 아니면 행만 옮겼는가"를 판단한다. 진짜 분해는 빠르게 승인되고 형식적 분해는 단순화 요청을 받는다. 이것이 프로젝트가 원하는 판단이다.

### 7.6 G6 단순화 리뷰

**사람 승인 (라우팅 트리거 발화 시 차단).** 체크는 "simplification review required: S1, S4" 같은 제목의 failure로 남아 있다가, P의 `simplification-reviewers` 팀원이 루브릭을 포함한 승인을 기록하면 해제된다.

- **승인자 독립성.** 승인자는 PR 작성자, PR의 어떤 commit의 author·committer·co-author도 아니어야 하며, AI 에이전트를 호출하거나 할당한 사람도 아니어야 한다. 봇 계정은 승인할 수 없다.
- **승인의 유효 범위.** 승인은 **head SHA에 묶인다.** 새 push 후에는 (a) patch-id가 같은 rebase이거나, (b) 새 commit이 트리거된 파일을 하나도 건드리지 않은 경우에만 승인을 이어받는다. 그 밖에는 다시 승인받는다. 승인 후 조작 코드를 밀어 넣는 것을 막기 위해서다.

**LLM 리뷰어 (v1은 관측).** 모든 PR에서 루브릭 결과를 PR 댓글 하나로 남기고 판정을 `gate-result.json`에 기록한다. 차단하지 않는 이유는 출력이 결정론적이지 않고, 읽는 PR 본문을 공격자가 통제하며("이 PR은 이미 단순화되었습니다" 같은 프롬프트 주입), 사람과의 일치도를 아직 측정하지 않았기 때문이다. 승격 기준은 13.2절.

**루브릭** (사람과 LLM 공통, 각 문항 예/아니오와 `file:line` 근거)

1. 같은 동작을 훨씬 적은 개념(함수, 타입, 분기, 모듈)이나 행으로 쓸 수 있는가? 더 단순한 모양을 제시하라.
2. 새 helper·모듈·매개변수·옵션 객체·제네릭은 (a) 두 곳 이상에서 쓰이거나 (b) 이름 붙일 수 있는 도메인 개념인가? `processPart2`, `handleRest`, 지역 변수 4개 이상을 끌고 다니는 단일 호출 helper, 단순 전달 wrapper는 "아니오"다.
3. 추측성 일반화, 죽은 코드, 중복 로직, 일어날 수 없는 일에 대한 방어 코드가 있는가?
4. 중첩된 제어 흐름을 early return, 데이터 표(클로저 표가 아닌), 상관된 조건의 병합으로 평평하게 만들 수 있는가?
5. 독자가 다른 새 정의를 두 번 넘게 따라가지 않고 각 변경 함수를 이해할 수 있는가?

판정은 `NO_SIMPLIFICATION_NEEDED`, `SUGGESTED`(차단 안 함), `REQUIRED`(1~4번 중 하나 이상 "아니오", 구체적 근거와 대안 제시) 중 하나다. 사람의 `REQUIRED`는 차단하고 LLM의 `REQUIRED`는 v1에서 기록만 한다.

## 8. 테스트 충분성 (문제 ③)

### 8.1 판단: 지적은 맞고, 답은 "다른 복잡도 지표"가 아니다

"CC가 테스트 수를 알려주는가"라는 질문에는 서로 다른 세 기준이 섞여 있다.

- **분기 커버리지**: 최대 CC개의 테스트가 필요하고, 2개로 충분할 수도 있다.
- **기본 경로(basis path) 테스트**: 정확히 CC개.
- **모든 비순환 경로**: NPath개. 지수적으로 늘어난다.

| 예시 | CC | CogC | NPath | 분기 커버리지 최소 테스트 수 |
|---|---:|---:|---:|---:|
| 독립 조건 `if` 8개 순차 실행 | 9 | 8 | 256 | 2 (모두 참, 모두 거짓) |
| `if` 3단 중첩 | 4 | 6 (1+2+3) | 4 | 4 |

두 모양에서 NPath는 필요한 최소 테스트 수와 **반대 방향**으로 움직인다. 조건이 서로 상관되어 있으면 2개로도 부족하다. 어떤 지표도 필요한 테스트 수를 예측하지 못하므로, 테스트 게이트는 **변경된 분기가 실제로 실행되었는지, 테스트가 약화되지 않았는지**를 직접 본다.

### 8.2 NPath: v1에서 제외

| 이유 | 내용 |
|---|---|
| TS 도구 부재 | ESLint 플러그인을 찾지 못했다. `eslint-plugin-sonarjs`에는 Cognitive Complexity(S3776)만 있다. NPath는 PMD·Checkstyle(Java), PHPMD(PHP), OCLint(C 계열)에만 있다 |
| 수치 불안정 | 지수적으로 커서 포화·오버플로 처리가 필요하고 도구마다 정의가 다르다. 문제 ①을 다시 만든다 |
| 잘못된 신호 | 리뷰어가 받아들이는 평평한 가드절·검증 체인을 가장 복잡한 코드로 판정하고, 실행 불가능한 경로도 센다 |
| 분할 조작을 보상 | 함수 단위 지표라 함수를 나누면 동작 변화 없이 크게 낮아진다. 문제 ②를 악화시킨다 |
| 이미 대부분 포함 | cccc의 CogC는 nesting과 논리 연산자 연속을 선형으로 가산한다 |

### 8.3 G4 변경 코드 테스트와 무결성 (v1부터 차단)

- **실행.** 테스트가 통과해야 하며, 실행된 테스트가 0개면 INCONCLUSIVE다(`passWithNoTests` 금지).
- **무결성: 차단** (B→C 비교로 기계적으로 검사)
  - 양쪽 JSON/JUnit 리포트의 테스트 ID 비교. C에서 사라진 테스트는 `gate-owners` 승인이 필요하다(waiver 대상 아님).
  - 새로 생긴 `.only`, `.skip`, `xit`, `todo`, `fails`.
  - assertion이 없는 새 테스트.
  - 커버리지·테스트·Stryker·tsconfig 설정 약화, 새 ignore 주석, 새 `eslint-disable`. 정책 변경으로 보아 독립 승인이 필요하다.
- **무결성: S7 라우팅**
  - 테스트별 assertion 수 감소, 약해진 matcher(예: `toEqual` → `toBeDefined`), 스냅샷 갱신. 정당한 경우가 있어 사람이 판단한다. AI 수정 루프에는 12.2절에 따라 금지된다.
- **한계.** "새 동작에 맞는 테스트가 있는가"는 근사만 가능하다. 커버리지(G5)와 변이(G7)가 대리 지표이며, 테스트가 올바른 동작을 검증하는지는 기계적으로 확인할 수 없다.

### 8.4 G5 변경 분기 커버리지 (관측 3~4주 후 개수 기준 차단)

- **입력.** B·C 트리, `git diff -U0`, Istanbul 형식 `coverage-final.json`. 분기 위치를 담은 `branchMap`이 있어야 하므로 이 형식을 요구한다.
- **도구 사실.** Vitest 3.2 이상은 V8 커버리지를 AST 기반으로 재매핑해 Istanbul과 같은 결과를 낸다고 문서화되어 있으며, Vitest 4에서는 이 방식만 남았다. c8과 Jest V8 provider는 재매핑하지 않아 분기 수가 다를 수 있다. 그래서 provider와 버전을 M에 고정한다(문제 ①의 원칙). Vitest의 `coverage.include` 기본값은 테스트가 import한 파일만이어서 **어떤 테스트도 import하지 않는 변경 파일이 보고서에서 조용히 사라진다.** `include`를 변경 파일로 명시한다. `reportOnFailure`의 기본값은 false라 테스트가 실패하면 보고서가 없으므로 true로 설정한다. diff-cover와 Codecov patch status는 행 기준이라 분기를 보지 않는다. `--changedSince`는 테스트 선택이지 커버리지가 아니다.
- **지표.** 실행되지 않은 변경 분기 결과 수, 실행되지 않은 변경 행 수, 보고서에 없는 변경 파일 수.
- **임계값.** 절대·개수 기준이며 최소 분모를 둔다. 예: 미실행 분기 결과가 max(2, 10%)를 넘거나, 변경된 export 함수의 실행 횟수가 0이면 FAIL. 프로젝트 전체 비율 래칫은 쓰지 않는다.
- **결정론.** 커버리지 정책, 제외 목록, ignore 주석 허용 목록은 P에서만 온다. 추가된 ignore 주석은 허용 목록에 없으면 미실행으로 센다.
- **상태.** 보고서 누락, provider 불일치, crash, 재시도 간 결과 불일치는 INCONCLUSIVE. 실행 가능한 변경 행이 없으면 NOT_APPLICABLE.
- **한계.** 분기 은닉 변환(7.2절 f, f′, i)은 커버리지를 *쉽게* 만든다. 그래서 G5는 분할 조작의 대응책이 아니며 S9가 그 역할을 맡는다.

### 8.5 G7 변이 테스트 (관측)

StrykerJS의 `--mutate`는 행 범위(`file:5-7`)를 받으므로 diff hunk를 그대로 넘길 수 있다. `--incremental`은 git이 아니라 자체 저장 보고서와 비교하고 의존성·스냅샷 변경을 감지하지 못한다. assertion이 실제로 무언가를 검증하는지 기계적으로 확인하는 유일한 방법이지만, 죽일 수 없는 변이와 timeout 처리 때문에 차단하기에는 잡음이 크다. 살아남은 변이를 PR 댓글로 보여 준다.

### 8.6 복잡도와 테스트 엄격도의 연동: v1에서는 하지 않는다

"CogC가 높은 단위는 변이 점수나 분기 커버리지 100%를 요구한다"는 연동은 방향은 맞지만 v1에는 과하다. 한도 바로 아래로 코드를 맞추면 더 엄격한 요구를 피할 수 있어 **새로운 조작 동기**(절벽)를 만든다. 테스트 판정이 단위 대응에 묶이고, 임계값을 정할 데이터도 없다. v1은 데이터만 기록한다. 가장 유력한 v1.5 후보는 "15를 넘는 기존 단위를 수정하면 그 단위의 변경 분기 결과를 모두 실행해야 한다"이다. 기존 부채는 값싸게 만들어 악용할 수 없기 때문이다.

**복잡도 게이트에는 테스트 입력을 넣지 않는다.** 불안정한 테스트가 복잡도 판정을 바꾸지 않게 하기 위해서다. 복잡도 PASS로 테스트 의무가 면제되지 않고, 테스트 PASS로 복잡도 의무가 면제되지 않는다.

## 9. 판정 상태, 종료 코드, 산출물

### 9.1 상태

| 상태 | 의미 | Runner 종료 코드 | GitHub check 결론 |
|---|---|---|---|
| `PASS` | 측정이 완전하고 정책을 충족 | 0 | `success` |
| `NOT_APPLICABLE` | 승인된 범위 안의 변경 파일 없음 | 0 | `success` (제목 "N/A"). **`skipped`·`neutral` 금지** |
| `ACCEPTED_WITH_WAIVER` | FAIL이었으나 모든 위반이 유효한 waiver로 덮임 | 0 | `success` (제목에 waiver 항목) |
| `FAIL` | 정책 위반 확인. 작성자가 조치 가능 | 1 | `failure` |
| `INCONCLUSIVE` | 측정을 신뢰할 수 없음 | 2 | **`failure`** (제목 "INCONCLUSIVE: 사유") |

**주의.** GitHub는 필수 체크의 `neutral`과 `skipped`를 통과로 취급한다. INCONCLUSIVE는 반드시 `failure`로 낸다. 이 종료 코드는 cccc 자체의 종료 코드(0 성공, 1 한도 초과, 2 사용 오류)와 별개의 계약이다. 필수 체크는 문서만 바뀐 PR에서도 실행되어 NOT_APPLICABLE을 기록해야 하며, 실행이 빠진 것을 통과로 처리하지 않는다.

알려진 위반과 측정 오류가 함께 있으면 둘 다 보고하고 집계는 FAIL이 우선한다(4.2절). 삭제만 있는 변경은 삭제 기록과 남은 대상 분류를 확인한 뒤 NOT_APPLICABLE이다. 선언 파일처럼 함수가 0개인 파일은 측정과 residue 검증을 거쳐 PASS가 될 수 있다.

## 10. 신뢰 경계와 우회 방지

### 10.1 실행 경계

- **G1·G2·G3과 집계기는 PR 코드를 실행하지 않는 게이트 서비스에서 돈다.** 게이트 서비스는 조직이 운영하는 GitHub App 백엔드로, PR 이벤트를 받아 git blob을 가져와 cccc, ESLint(P 설정, 게이트 저장소 플러그인), dependency-cruiser를 실행하고 check를 쓴다. App의 비공개 키는 이 서비스에만 있다. 키를 Actions 시크릿에 두면 같은 저장소 브랜치에서 온 PR의 workflow가 `pull_request`로 그 시크릿을 읽어 필수 체크를 위조할 수 있다. AI 에이전트의 브랜치는 대개 같은 저장소에 있다.
- **필수 체크는 `quality-gate` 하나이며 예상 출처를 게이트 App으로 고정한다.** 출처를 "GitHub Actions"로 고정하는 것은 소용이 없다. PR의 workflow도 GitHub Actions로 실행되기 때문이다.
- **G4·G5·G7은 PR 코드를 실행한다.** `pull_request` 또는 `merge_group`에서 `contents: read`, 시크릿 없이, 일회용 runner로 실행한다. 시크릿은 환경(environment) 범위로 묶어 이 작업들이 접근할 수 없게 한다. 그 산출물은 집계기에 대한 비신뢰 입력이며, 집계기는 게이트 저장소의 고정된 workflow 파일·SHA로 실행된 run의 산출물만 받는다. 이 workflow는 조직 ruleset의 "Require workflows to pass before merging"으로 붙이고 `merge_group` 트리거를 선언한다(조직의 GitHub 요금제에서 이 기능을 쓸 수 있는지 P0에서 확인).
- **`pull_request_target`은 쓰지 않는다.** base 브랜치의 workflow를 쓰기 토큰·시크릿과 함께 실행하므로, PR 코드를 checkout해 PR이 통제하는 것을 무엇이든 실행하면 그 권한으로 코드가 실행된다. `npm ci`의 postinstall, 테스트, PR의 `eslint.config.js`·`vitest.config.ts`·Babel 플러그인이 모두 해당된다.
- **AI 수정 루프**는 시크릿이 없는 격리된 작업에서 실행한다.
- **CODEOWNERS**를 `.github/**`, 정책 파일, `.gitattributes`, `.gitmodules`, lint·테스트·커버리지 설정에 둔다.
- **캐시 없음.** cccc는 `--no-cache`로 실행하고, `actions/cache` 복원물이 판정에 들어가지 않는다.

### 10.3 위협 모델

PR 코드를 실행해 얻는 증거(테스트 결과, 커버리지)는 악의적인 PR 코드가 위조할 수 있다. 이 게이트들은 **최적화 압력**, 즉 AI 에이전트나 서두르는 사람이 테스트·설정을 약화시키는 것을 막는다. 악의적인 기여자는 막지 않는다. 그 부분은 보호 경로 규칙과 사람 리뷰가 맡는다. G1~G3은 PR 코드를 실행하지 않으므로 이 한계가 없다.

## 11. waiver와 측정 override

### 11.1 waiver: FAIL에 대한 기록된 위험 수용

긴 dispatcher나 명시적인 상태 전이처럼 수치만 줄이는 리팩터링이 오히려 읽기 어려운 경우가 있다. 이때는 무의미한 분할을 강요하지 않고 좁은 waiver를 승인한다.

- **요청.** PR 댓글 `/gate-waive gate=complexity unit="src/a.ts::Parser>run#method[0]" metric=cogc ceiling=22 reason="…"`. 게이트 결과가 각 위반의 정확한 `unit` 키(5.4절)를 출력하므로 복사하면 된다.
- **승인.** P의 `waiver-approvers` 팀원이 `/gate-waive-approve <id>`. 게이트 서비스가 API로 팀 소속을 확인한다. 승인자 독립성은 7.6절과 같다(작성자, commit 참여자, 에이전트 호출자, 봇 제외). 승인자가 `simplification-reviewers` 소속이면 같은 승인으로 S6도 해제한다.
- **범위.** `(gate, unit 키, metric, ceiling)`이며 C blob SHA에 묶인다. 해당 PR에서 단위 값이 ceiling 이하이고 단위 키가 유지되는 동안만 유효하다. 와일드카드, 파일 단위, PR 단위 waiver는 없다.
- **waiver 불가.** INCONCLUSIVE(측정 override 대상)와 G4 무결성 위반(사라진 테스트, `.only`/`.skip`, 보호 경로 변경)은 waiver로 처리하지 않는다. 후자는 P 변경 승인으로만 처리한다.
- **예산.** PR당·분기당 waiver 예산을 둔다. waiver 비율이 PR의 5%를 넘으면 임계값이 틀린 것으로 본다.
- **병합 후: v1은 병합된 waiver 단위를 원장과 90일 이슈로 추적한다.** 모든 waiver를 게이트 저장소의 `waivers.jsonl` 원장(PR, 단위, 지표, 값, 승인자, 사유, 날짜)에 추가하고 90일 기한의 `complexity-debt` 이슈를 자동으로 연다. 원장 크기와 연령을 추적한다.
  - Codex는 "임시 예외를 영구 baseline 허용치로 전환하지 않는다"고 했지만, 그 자신의 `max(T, B)` 규칙에서는 병합된 waiver 단위가 자동으로 다음 PR의 기준이 된다. 이를 막으려면 PR 간 단위 정체성을 가진 영속 부채 레지스트리가 필요하고, 그것은 v1에서 만들지 않기로 했다. "원장에 있는 단위는 신규로 취급"하는 재강화는 v2 indexer 결정에 따라 정한다.

### 11.2 측정 override: INCONCLUSIVE에 대한 조치

1. **자동 재시도 1회.** timeout, I/O 오류, runner 소실 같은 일시적 원인.
2. **작성자가 고칠 원인**은 안내와 함께 보고한다. 구문 오류, 1000단계 초과 중첩, 비 UTF-8 파일, 설정 없는 저장소의 JSX-in-`.js`. 이것들은 override 대상이 **아니다.** override를 허용하면 일부러 심어서 파일을 영구히 측정 밖으로 빼는 경로가 된다.
3. **게이트 담당자 원인**: `MEASURER_MISMATCH`, `SCHEMA`, `INVARIANT_VIOLATION`, `NONDETERMINISM`, 그리고 `tsc`는 통과하는데 oxc가 거부하는 문법 중 **P의 파서 지연 목록에 있는 것**. 이때만 `gate-owners` 팀원(작성자 아님)이 측정 override를 건다. override는 `(gate, 사유, 파일 경로, C blob SHA)`에 묶여 파일이 바뀌면 사라진다. 효과는 그 파일을 `unmeasured`로 표시하고, ESLint `complexity`로 관측용 대체 측정을 남기고, 단순화 리뷰를 필수로 만들고(S6), 게이트 저장소에 이슈를 여는 것이다. **override는 FAIL을 PASS로 바꾸지 않는다.** "측정할 수 없음"을 "사람이 측정함"으로 바꿀 뿐이다.
4. **SLO.** INCONCLUSIVE는 PR의 1% 미만. 넘으면 게이트 결함으로 다룬다.

"게이트 건너뛰기" 라벨은 없다. 판정을 바꾸는 길은 세 가지뿐이다. waiver(FAIL 대상), 측정 override(INCONCLUSIVE 대상), P 변경(게이트 저장소 리뷰). 긴급 hotfix는 조직의 기존 ruleset 관리자 우회를 쓰며, GitHub가 감사 기록을 남기고 매주 사용 내역을 보고한다. 긴급 병합을 정상 PASS로 위조하지 않는다.

## 12. AI 수정 루프 계약

### 12.1 에이전트에 전달하는 피드백

`gate-feedback.json`(같은 내용을 PR 댓글로도 표시)에는 위반마다 단위 키, `file:line`, 지표, 값, 한도, 기존 기준값, 발화한 트리거와 증거, 유지해야 할 동작 검증이 들어간다. cccc는 구문별 내역을 주지 않으므로 힌트는 3.3절 계산 규칙에서 나온 일반적인 내용으로 한정하고, 도구가 주지 않은 구문 단위 귀속을 주장하지 않는다.

에이전트 지시문은 다음을 명시한다.

> 지정된 단위의 복잡도를 줄이되 early return, 이름 있는 조건 함수, 데이터 표를 우선하라. helper는 이름 붙일 수 있는 개념이고 매개변수가 4개 이하일 때만 추출하라. 테스트와 설정을 바꾸지 마라. 다음은 단순화 리뷰에서 실패로 간주된다: 클로저 표, 논리 할당을 이용한 제어 흐름, 불리언 인덱싱, 범용 조합자, 즉시 실행 함수, 필드 초기화식 로직, context 객체를 통한 helper 연쇄, 문자열로 만든 함수.

보상 해킹을 하는 에이전트는 명시된 규칙에 반응하고, lint 규칙과 트리거가 그 규칙을 뒷받침한다.

### 12.2 금지 행위 (지시가 아니라 기계적으로 강제)

수정 루프의 diff가 다음을 건드리면 `FAIL(POLICY_PATH_MODIFIED)` 또는 G4 무결성 FAIL이며, 루프는 waiver를 신청할 수 없다.

- 게이트·도구 설정: `cccc.toml`, `.cccc.toml`, ESLint·dependency-cruiser·vitest·jest 설정, `tsconfig*.json`의 `strict*`, `.gitignore`, `.ignore`, `.gitattributes`, `package.json`의 `scripts.test`와 테스트 실행 플래그, CI workflow, waiver 원장
- 테스트: B에 있던 테스트 ID 삭제, `.only`/`.skip`/`xit`/`todo`, assertion 수 감소, matcher 약화, 스냅샷 갱신(`-u` 실행)
- 억제 주석: 추가된 `eslint-disable*`, `/* istanbul ignore */`, `/* v8 ignore */`, `@ts-ignore`, `@ts-nocheck`(P 허용 목록 제외)
- 측정 범위 밖으로 이동: `.ts`를 미측정 확장자로 변경, 제외·생성물 경로로 코드 이동

### 12.3 반복 한도

- 자동 재시도는 **최대 2회**다. 그 후 전체 이력과 함께 사람에게 넘긴다.
- **조기 중단**: 시도 후 위반 집합이 그대로인 경우(진전 없음), 수정 후 새 트리거가 발화한 경우(예: S1이나 S9. 루프가 재분배하거나 숨기고 있다는 뜻이므로 G6로), 12.2절 FAIL이 발생한 경우.
- 모든 재시도는 같은 B에 대해 측정한다. B는 이전 시도가 아니라 병합 기준이므로, 루프가 중간 상태를 커밋해 스스로 래칫을 걸 수 없다.
- 기능 삭제나 정책 완화를 해법으로 제안하지 않는다. 원래 요구사항과 동작 검증을 유지한 채 고친다.

| **P2 복잡도·구조 enforce** | P1 검토 후 | + G1 CogC 규칙, + G2 차단 규칙 전체, + G3 새 금지 간선, + G6 라우팅 트리거(S1~S7, S9~S11) 사람 승인 | CC, 포함 CogC, G5, G7, LLM | 13.3절 마찰 지표가 목표 범위 |
| **P3** | +4주 | + G5 개수 기준 (보정 기준 충족 시) | CC 보조 차단·길이 FAIL·LLM 승격 결정 | |

shadow 기간에도 기존 build, typecheck, test, security 의무는 그대로 유지한다. 적용 범위는 승인된 저장소부터 시작해 INCONCLUSIVE, 불필요한 리팩터링, waiver 반복의 원인을 확인한 뒤 넓힌다.

### 13.2 프로젝트 질문에 맞춘 보정

1. **정답 데이터 만들기.** shadow 기간의 모든 PR에서 사람 리뷰 댓글을 "단순화 요청인가"로 분류하고 `file:line`에 연결한다. LLM 분류기를 쓰되 100개를 수동 표본 검사해 정확도 90% 이상을 확인한다. 단순화 댓글이 단위 범위 안이나 시작 행 ±5행에 달리면 그 단위는 "리뷰어 지적"이다. 리뷰어도 놓치므로, 게이트와 리뷰어가 엇갈린 PR 50개를 매주 선임 리뷰어 두 명이 다시 분류해 리뷰어 재현율도 측정한다.
2. **후보 지표·임계값별 계산**(CogC 10/12/15/18/20, CC 15~30, 길이 60~150, 포함 CogC 20~35): 정밀도 = P(리뷰어 지적 | 임계값 초과), 재현율 = P(임계값 초과 | 리뷰어 지적), PR당 FAIL 비율.
3. **차단 임계값 선택.** 정밀도 0.6 이상 **이고** PR당 FAIL 비율 10% 이하인 가장 낮은 임계값을 고른다. CogC 15의 정밀도가 0.5 미만이면 이 코드베이스에는 너무 엄격한 것이므로 원칙을 고집하지 말고 올린다. 12에서 정밀도 0.7 이상이고 FAIL 비율이 예산 안이면 12로 강화한다. 차단 게이트의 목표는 재현율이 아니다. 놓친 사례는 리뷰 게이트의 몫이다.
4. **트리거.** "리뷰어가 트리거 증거에 대해 수정을 요청함" 대비 정밀도 0.3 이상. 트리거는 FAIL이 아니라 리뷰어의 시선 한 번이므로 기준이 낮다. 0.15 미만인 트리거는 조정하거나 폐기한다. S1은 정직한 리팩터링에도 발화하므로 특히 주시한다.
5. **LLM 리뷰어 승격.** 사람 루브릭 판정과 Cohen's κ ≥ 0.6(200개 PR 이상), 사람이 틀렸다고 보는 `REQUIRED` ≤ 5%, 프롬프트 주입 레드팀 세트 통과. 그때도 트리거(LLM `REQUIRED`가 사람 리뷰로 라우팅)가 될 뿐 단독 차단자가 되지 않는다.

### 13.3 운영 지표 (주간)

- **일치도(핵심 지표)**: 게이트 FAIL·트리거와 사람 단순화 요청 사이의 정밀도·재현율.
- **누락**: 게이트를 통과해 병합된 뒤 30일 안에 같은 단위에 "단순화" 리팩터링이나 revert가 일어난 PR.
- **마찰**: PR당 FAIL 비율(목표 ≤ 10%), waiver 비율(목표 ≤ 3%, 5% 초과 시 임계값 재검토), INCONCLUSIVE 비율(< 1%), `UNMATCHED_OVER_BUDGET` 비율(v2 indexer 판단 근거), G6 승인 대기 시간, 병합까지 추가 소요 시간 중앙값.
- **AI 루프**: 2회 안 수렴률(목표 ≥ 80%), 수정 후 S1·S9 발화 비율(재분배·은닉 비율), 12.2절 위반 시도 횟수.
- **부채**: waiver 원장 크기·연령, 수정·감소된 15 초과 기존 단위 수.
- **KPI가 아닌 것**: 평균·합계 복잡도. 분할과 변경량을 보상한다.

### 13.4 게이트 오작동 시 대응

- **판단 기준.** 1시간 동안 FAIL이나 INCONCLUSIVE 비율이 직전 4주 평균의 3배를 넘거나, `quality-gate`가 15분 넘게 보고되지 않으면 장애로 본다.
- **완화.** `gate-owners` 2인이 P에서 해당 하위 게이트의 `mode`를 `enforce`에서 `observe`로 바꾸는 commit을 병합한다. 저장소 설정과 필수 체크는 건드리지 않는다. 집계기는 다음 실행부터 그 게이트를 집계에서 뺀다.
- **집계기 자체 장애.** 11.2절의 ruleset 관리자 우회만 쓴다. 필수 체크를 해제하지 않는다.
- **복구.** 수정 후 14절 픽스처와 최근 200개 PR 재생을 통과하면 `enforce`로 되돌린다. 장애 기간에 병합된 PR은 사후에 다시 측정하고 결과를 이슈로 남긴다.

## 15. Codex 초안과의 차이

| # | Codex v0.1 | 본 기획서 | 이유 |
|---|---|---|---|
| 1 | CC 12와 CogC 15 공동 차단 | CogC 15만 차단, CC 관측 | cccc의 CC는 `?.`·`case`·추출 함수마다 올라 리뷰어 판단과 어긋나고 분할을 벌한다. 도구 간 차이도 가장 크다 |
| 2 | "중첩 함수도 검사" | 콜백이 부모에 더해지지 않는 맹점을 명시하고 `max-nested-callbacks` 차단, S2, 포함 CogC 기록 | 실측된 cccc 특성. cccc의 15는 Sonar의 15보다 관대하다 |

| 6 | 파싱 오류 시 "복구된 일부 결과" 위험 | 실제 위험은 **파일 전체 0점 + exit 0**. C쪽은 INCONCLUSIVE(override 불가), B쪽은 신규 취급 | 실측 |
| 7 | 측정 예시 명령만 제시 | 인자 계약, 검증 항목 9개(stderr, 빈 출력, manifest 대조 포함) | 실측 동작 |
| 8 | checkout 기반 (명시 없음) | git blob에서 직접 구성 | `.gitattributes` 한 줄 우회 재현 |
| 9 | "이미 채택된 lint 규칙만" | P가 최소 하한을 정의, 신규 위반에만 차단, `--no-inline-config` | 게이트 강도가 저장소의 우연에 좌우되지 않도록 |
| 10 | 함수 분할은 "PASS의 보장 범위 제한"만 | 분기 보존(S1)·분기 은닉(S9)·분할 밀도(S10) 트리거로 단순화 리뷰 필수화, 이동 기준 비교 | 실측상 17종 중 대부분의 조작이 통과. 리뷰 라우팅 없이는 프로젝트 질문에 답하지 못한다 |
| 11 | 길이를 분할 대응책처럼 언급 | 길이는 분할을 보상한다. 트리거로만 사용 | ESLint 실측 |
| 12 | 비용 0 구문·동적 코드 언급 없음 | `&&=`·`\|\|=`·`??=`, 조합자, Function 생성자 계열 대응 | 실측: CogC 24 → 1, 단위 소실 |
| 13 | "임시 예외를 영구 baseline으로 전환하지 않음" | 원장 + 90일 이슈. 재강화는 v2 | Codex의 `max(T, B)`와 모순 |
| 14 | 도구 변경 시 재기준화 | 불필요(baseline 비저장). 업그레이드는 픽스처 + 200 PR 재생 | B·C를 항상 같은 바이너리로 측정 |
| 15 | 정책 보호는 원칙 수준 | 게이트 서비스(App 키 격리), App 출처 고정, `merge_group`, `pull_request_target` 미사용, `cccc-action` 미사용 | GitHub에서 실제로 우회 가능한 경로 |
| 16 | INCONCLUSIVE의 GitHub 표현 미정 | `failure`로 고정, `neutral`·`skipped` 금지 | GitHub는 이들을 통과로 취급 |
| 17 | 테스트 게이트는 "기존 체계 재사용" | G4(v1부터 차단), G5(관측 후 개수 차단), G7(관측)을 게이트 묶음에 포함 | 문제 ③의 실제 답 |
| 18 | 승인자 독립성: "작성자와 독립" | commit 참여자, 에이전트 호출자, 봇까지 제외. 승인은 head SHA에 묶음 | AI PR에서는 호출한 사람이 사실상 작성자다 |

**유지하는 Codex의 판단**: 측정기와 판정기의 분리, AI 작성 여부와 무관한 적용, NPath 비도입, 테스트를 복잡도 게이트와 분리, 지표 간 상쇄 금지, 기존 부채 비악화, 매 실행 B 재측정, 종료 코드 0/1/2, 자동 재시도 2회, 평균 복잡도를 KPI로 쓰지 않음.

## 17. 남은 위험

- **기계로 구별할 수 없는 영역이 크다.** 정직한 분할과 형식적 분할, 데이터 표와 클로저 표, 과잉 추상화(규칙 엔진, 전략 계층)는 사람 판단에 의존한다. 특히 S1은 정직한 리팩터링에도 발화한다. 트리거 정밀도가 낮으면 리뷰어 피로가 쌓이므로 13.2절 보정으로 관리한다.
- **cccc의 계산 특성은 고정해도 사라지지 않는다.** 논리 할당 무비용, 콜백 비가산, 이름 기반 재귀 판정은 일관되게 틀린다. upstream이 개선되기 전까지는 G2와 트리거로 보완한다.
- **동적 코드 생성의 형태는 열거로 다 막을 수 없다.** 7.4절 목록은 재현한 경로를 막을 뿐이며, S11 단위 소실과 사람 리뷰가 최종 방어선이다.
- **파서 지연.** oxc가 새 문법을 늦게 지원하면 정상 코드가 INCONCLUSIVE가 된다. P의 파서 지연 목록, 측정 override, INCONCLUSIVE SLO로 관리한다.
- **PR 코드를 실행하는 게이트의 증거는 위조될 수 있다.** 악의적 기여자 방어는 이 기획의 범위 밖이다.
- **단순화 리뷰가 병목이 될 수 있다.** 트리거 발화 비율과 승인 대기 시간을 P1에서 측정하고, LLM 리뷰어 승격으로 부담을 줄일 수 있는지 판단한다.

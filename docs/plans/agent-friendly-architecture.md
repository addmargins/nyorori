# nyorori를 에이전트 친화적으로 재구성하는 계획

작성: 2026-10-30. 대상: `claude/agent-friendly-architecture-v8v3ia` (PR #1 head `cbcb10a` 위에 커밋 5개).

## 요약

목표는 파일 하나만 열고, 가장 가까운 예를 복사하고, 컴파일되는 최단 경로를 택하는 에이전트도 올바른 결과를 내는 저장소다. 리뷰에 쓰던 노력을 구조, 타입, 기계적 검사로 옮긴다.

증거는 세 곳에서 모았다. PR #1의 커밋 50개와 리뷰 기록, 코드 전체의 정적 분석, 그리고 운영자의 Claude Code 세션 39개다. 여기서 반복 실수 클래스 40개를 뽑았고, 그중 10개가 세 관점의 적대적 검증을 통과했다.

가장 큰 발견은 이 저장소가 자기 게이트를 통과하지 못한다는 점이다. nyorori 자신의 커밋 50쌍을 nyorori로 판정하면 25쌍이 차단된다. 인지 복잡도 한도(15)를 넘는 새 함수가 164건이고, 이미 한도를 넘은 함수를 수정 라운드가 더 키운 경우가 49건이다.

이 브랜치에는 수정 네 가지를 넣었다. 각각 과거 커밋에서 실패하고 수정 뒤에 통과하는 것을 보였다. 이 저장소 이력 52쌍을 다시 판정해도 결과가 모두 같다.

1. 닫힌 집합(트리거 id, 게이트 모드, 사유 코드)의 출처를 `src/types.ts` 하나로 만들었다. 실제 드리프트 3건을 고쳤다.
2. CI에서 게이트가 자기 PR을 판정한다.
3. 커밋 id 검사와 오류 문구 추출을 헬퍼 하나씩으로 모았다. 사본 33개를 지웠고, 갈라져 있던 의미 하나를 통일했다.
4. `AGENTS.md`에 규칙마다 그것을 집행하는 장치를 짝지었다.

새 에이전트 8명으로 전후를 비교했다. 측정한 함정 비율은 전후 모두 0이라 차이가 없었다. 다만 "후"에서는 새 사유 추가에 필요한 편집이 두 곳에서 한 곳으로 줄었다. 또 후보 전원이 부하에서 흔들리는 테스트를 만났고, 같은 리팩터링을 세 가지 이름으로 했다(8절).

다음 순서는 게이트 계약 통일이다(클래스 C05, C01, C03).

## 4. 운영자가 에이전트를 조종하는 방식

세션 기록에서 반복되는 패턴이다. 발화 원문 인용은 공개 저장소에 넣지 않았다.

- **재현부터.** 버그 제보를 받으면 "사실인지, 재현되는지 확인한 뒤 고치라"는 같은 지시를 네 세션에서 반복했다.
- **실행하지 않은 결론을 되묻는다.** 읽기만으로 84건을 오탐 처리했다가 실제 버그가 섞여 있던 사례, CI가 깨진 PR을 끝났다고 넘긴 사례가 있다.
- **한 에이전트의 판단을 믿지 않는다.** "서로 다른 관점의 서브에이전트"에게 다시 검토시키는 지시가 다섯 세션 이상에 있다. 기계적으로 판정할 수 있는 것은 두 번째 에이전트 대신 명령 하나로 옮기는 편이 싸다.
- **요청 밖 변경을 되돌린다.** 요청하지 않은 이름 변경, 중복 PR, 범위 밖 기능이 그 예다.
- **보고 형식.** 한국어, 결론 먼저, 붙여넣을 수 있는 본문, PR에 스크린샷과 배경을 원한다.
- **큰 작업은 "전문 서브에이전트 팀, 메인 에이전트는 조율"로 맡긴다.** 이 지시로 PR #1을 만들 때 병렬 빌더 A~E가 게이트를 따로 썼다(`docs/debate/disputes.md`). 통합 커밋 `75a4d10`은 그 차이를 어댑터로 덧댔다. 검증된 상위 클래스 C01, C04, C05가 여기서 나왔다. 병렬로 나누기 전에 공유 계약을 코드로 먼저 착지시켜야 한다는 것이 이 계획의 가장 중요한 근거다.

## 6. 회귀 오라클

리팩터링이 판정을 바꾸지 않았다는 증거는 이 저장소 자신의 이력이다. 커밋 쌍 52개를 `nyorori replay`로 판정하고, 판정 요약(`computeDelta`)과 `gate-summary.md`, `gate-feedback.json` 텍스트를 기준선과 비교한다. 이 문서의 모든 "52쌍 동일"은 판정 차이 0, 텍스트 차이 0을 뜻한다.

```bash
# pairs.json: 연속 커밋 쌍 50개 + 사람 브랜치 + PR 전체, 정책은 tests/coverage/mutation 관측
node dist/cli.js replay --repo <clone> --pairs pairs.json --policy policy.json --out <dir> --cccc "$NYORORI_CCCC" --jobs 2
```

이 오라클은 아직 CI에 없다. 데이터셋 생성 스크립트와 비교 스크립트를 `scripts/`로 옮기는 일이 남은 계획 항목이다.

## 7. 설계: 다음 트랙

### 7.1 게이트 계약 (C05 + C01 + C03, 최우선)

문제는 새 게이트를 쓰는 에이전트가 가장 가까운 `evaluate.ts`를 복사한다는 점이다. 그러면 레코드를 손으로 만들고, 상태를 네 번째 방식으로 도출하고, 증거를 문장에 담는다. 파이프라인은 또 어댑터를 붙인다.

두 후보를 비교했다.

- **A1. 봉인된 리포트 빌더.** 파이프라인이 게이트 id, 정책 모드, 지문을 아는 `report`를 게이트에 넘긴다. 게이트는 `report.violation(...)`, `report.trigger(...)`, `report.inconclusive(...)`만 호출한다. 레코드는 브랜드 타입이라 객체 리터럴은 타입 검사를 통과하지 못한다. `run.ts`의 손 연결 6개는 `Gate = { id, evaluate(ctx, report) }` 레지스트리 순회로 바뀐다.
- **A2. 타입 있는 발견 + 리듀서.** 게이트는 사유 코드로 구분되는 판별 유니언만 반환한다. 사유 레지스트리 표(사유 → FAIL/INCONCLUSIVE/트리거, 소유 게이트, waiver 가능 여부, 라우팅, 문구 템플릿) 하나가 결과를 만든다. README 사유 표도 이 레지스트리에서 생성한다.

권고는 A1을 기반으로 A2의 사유 레지스트리를 붙이는 것이다. A1은 게이트 하나씩 옮길 수 있어 오라클을 매 단위 확인할 수 있다. A2의 레지스트리는 C09의 "한 사실 두 표현"(`details.waivable`)과 C03의 문구 문제를 함께 없앤다.

`authorFixable`을 사유에서 파생하는 안은 측정 결과 기각했다. `src/git/tree.ts`는 같은 사유를 오류 코드에 따라 다르게 정하고, lint와 tests 게이트는 `PARSE_ERROR_CANDIDATE`를 `true`로 둔다. 그래서 빌더 인자로 남긴다.

이행 단위는 다음과 같다. 각 단위는 `tsc`, 테스트, 52쌍 오라클로 끝난다.

1. 빌더와 브랜드 타입을 추가하고 mutation 게이트(가장 작음)만 옮긴다.
2. coverage, deps, lint, tests, complexity 순으로 하나씩 옮긴다.
3. `fromEvaluation`, `splitEnforced`, `lintState`, `depsState`, `tests/evaluation.ts`를 삭제하고 `deriveState`를 하나로 만든다.
4. 레코드 리터럴을 막는 린트로 마무리한다.

예상 규모는 src 약 25파일이다.

증명 계획: 극성이 반대인 두 `deriveState`가 한쪽만 고쳐진 커밋, 그리고 지역 팩토리 `bad()`가 `fail()`을 복사한 `c514743`에서 새 린트가 빨강인지 보인다.

열린 질문이 하나 있다. 브랜드 타입이 기존 테스트 44곳의 위조 레코드와 어떻게 공존할지다. 테스트용 빌더를 `test/support`에 두는 안을 스파이크로 확인한다.

### 7.2 닫힌 집합 2단계 (C04 후속)

튜플은 착지했다. 다음은 구성원의 속성을 레지스트리 객체로 옮기는 일이다. 트리거의 라우팅 여부와 소유 게이트, 게이트의 정책 모드 경로와 실행 위치가 대상이다. 그러면 `policyMode`의 switch, `ALWAYS_ROUTING_TRIGGERS`, README 표가 레지스트리에서 파생된다. 7.1의 사유 레지스트리와 같은 모양으로 맞춘다.

### 7.3 공용 헬퍼 2단계 (C02 후속)

헬퍼 두 패밀리를 정리했다. 남은 것은 원자 쓰기(6곳 중 `VerdictStore`만 잠금과 UUID 없음), 자식 프로세스 env 조립(7곳, git 키 집합 3종), `JSON.parse(await readFile)`(8~12곳), sha256(9곳), realpath 상향(2곳, 의미 다름)이다. 지우는 방식은 경계에서 파싱하는 것이다. `JsonFile<T>`(zod 스키마와 경로를 묶은 읽기), `AtomicStore`, `ChildEnv` 빌더를 둔다. 남는 것만 `src/util`로 보내고 같은 방식의 린트로 막는다.

## 8. 에이전트 전후 평가

새 에이전트(sonnet) 8명에게 실제 작업처럼 쓴 요청 두 개를 줬다. 같은 문장을 "전"(`cbcb10a`) 작업공간 2개와 "후"(이 브랜치) 작업공간 2개에 줬다. 작업공간은 이력 없는 일반 사본이고, 후보는 평가라는 사실도 다른 후보도 몰랐다. 채점은 후보의 보고가 아니라 결과물로 했다. 차이를 보고 `tsc`, 린트, 빌드한 `dist`를 실행해 확인했다.

| 요청 | 함정 | 전 | 후 |
|---|---|---|---|
| R1. 기준 커밋이 없으면 새 INCONCLUSIVE 사유 `BASE_UNREACHABLE`로 보고 | 사유를 손 목록에 빠뜨려 `isWaivable()`이 참이 됨 | 0/2 (둘 다 waiver 모듈의 목록을 찾아 직접 고침) | 0/2 (목록이 튜플에서 파생되어 고칠 곳이 없음) |
| R2. replay 데이터셋에 선택 필드 `merge_base` 추가 | 커밋 id 정규식을 새로 씀 | 0/2 | 0/2 |

함정 비율에는 차이가 없다. 셀마다 두 번이라 2/2 대 0/2가 아니면 신호로 보지 않기로 미리 정했다. 차이는 필요한 편집의 수에서 났다. "전"의 R1 후보는 사유 하나를 넣으려고 두 파일의 목록을 고쳐야 했고, "후"는 한 줄이었다. "후"의 후보 둘은 보고에 "스키마와 waiver 집합은 이 배열에서 파생되므로 따로 고칠 곳은 없었다"고 썼다. R2는 과제 설계가 약했다. 같은 파일에 이미 `sha` 스키마가 있어 네 명 모두 그것을 복사했다. 함정이 생길 자리가 없었다.

평가가 의도하지 않은 두 가지를 보여 줬다.

- **테스트 스위트가 부하에서 흔들린다(C25).** 여덟 명 모두 전체 `npm test`에서 한 번 이상 실패를 봤다. `test/e2e/cli.test.ts`의 30초 타임아웃과 `test/complexity/regressions.test.ts`의 "1초 이내" 단언이었고, 따로 돌리면 통과했다. 원인을 확인한 후보는 없었다. 대부분 "부하 때문으로 보인다"고 추정하고 넘어갔다. 실패를 무시하는 습관을 저장소가 가르치고 있다.
- **같은 일을 네 가지로 했다(C14, C05).** R1 후보 네 명이 모두 `failedRunOutput`과 `authorityLine`을 새 모듈로 옮겼다. 파일 이름은 `failed.ts`, `failed-run.ts`, `inconclusive-run.ts`로 갈렸다. 함수 시그니처도 사유 문자열, `Inconclusive` 객체, 새 함수 `inconclusiveRunOutput`으로 달랐다. "실행 전체를 INCONCLUSIVE로 끝내는 한 가지 방법"이 코드에 없기 때문이다. 7.1의 게이트 계약이 이 자리를 맡아야 한다.

후보의 새 코드는 네 개 모두 자기 게이트를 통과했다(새 함수 CogC 15 이하, 매개변수 4개 이하).
